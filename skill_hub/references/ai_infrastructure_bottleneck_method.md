# AI Infrastructure Bottleneck Method

This reference is a shared method file for Skill 001, Skill 002, Skill 004, Skill 005, and any AI-infrastructure report route.

It adapts the valuable reasoning pattern from event-level public-research skill systems. It does not import data collection, scripts, or ticker-specific recommendations.

## Core Question

```text
What new AI workload or architecture change is forcing the infrastructure stack to reveal a scarce layer that the market has not fully priced?
```

Do not start with:

```text
Which AI stock is cheap?
```

Start with:

```text
What changed in the workload / architecture / deployment?
Which layer becomes constrained?
Who owns or enables the scarce capability?
Is the beneficiary obvious or still under-discussed?
What evidence would prove or disprove it?
```

## Four-Layer Map

### 1. Demand Driver

Name the specific demand driver:

- larger training clusters
- inference scaling
- long-context or agentic workloads
- custom ASIC adoption
- rack-scale systems
- CPO / optical interconnect
- HBM / memory bandwidth
- datacenter power density
- cooling, test, advanced packaging, or substrate pressure

Reject vague drivers such as "AI is growing" unless the packet ties them to a concrete workload, deployment, capex plan, customer, product transition, or architecture change.

### 2. Physical Or Technical Bottleneck

Identify the layer where scaling becomes harder, slower, more expensive, capacity constrained, or qualification constrained.

Common AI infrastructure bottlenecks:

- memory bandwidth / HBM capacity
- advanced packaging
- optical interconnect / photonics
- transceivers / lasers
- burn-in / test
- substrate / interposer
- thermal / power delivery
- datacenter power and cooling
- qualification and customer approval

### 3. Beneficiary Chain

Map more than the headline winner:

- prime beneficiary
- second-order supplier
- equipment vendor
- material supplier
- foundry / packaging / test provider
- power, cooling, and physical-infrastructure supplier
- customer that validates demand
- peer or context ticker that should not be treated as direct signal

### 4. Evidence Stack

Prefer events where several evidence types reinforce one another:

- customer signal
- supply-chain constraint
- earnings / guidance / order evidence
- capacity, backlog, pricing, capex, inventory, or management commentary
- specialist research or primary-source confirmation
- market reaction or benchmark-relative follow-through when available

Single-source bullish language is a lead, not proof.

## Signal Classification

Use this classification before turning an AI-infrastructure signal into a report conclusion:

| Label | Meaning |
| --- | --- |
| `early_discovery` | Signal appears before broad recognition or major price reaction. |
| `continuation_confirmation` | Prior runup exists, but the source adds new evidence that still matters. |
| `late_validation` | The thesis may be true, but most of it may already be known or priced. |
| `after_fact_commentary` | The source mainly explains a move that already happened. |
| `context_only` | The ticker validates demand or context but is not the focal beneficiary. |

## Reusable Search Pattern

```text
AI architecture transition
-> stressed layer
-> scarce capability
-> obvious winners vs overlooked beneficiaries
-> customer / qualification / funding / capacity proof
-> price-in check
-> discovery-stage label
-> report-use decision
```

## What Enters Skill 001-4

- Skill 001 uses this file to identify which reasoning actions from a case should be absorbed into the hub.
- Skill 002 uses it to translate workload and architecture changes into physical constraints and supplier exposure.
- Skill 003 uses it when a technical signal must become a PM-facing company or basket thesis.
- Skill 004 uses it as the AI-infrastructure specialization of scarce-layer mapping.
- Skill 005 uses it when public events need discovery-stage, evidence-stack, and price-in discipline.

## Guardrails

- Do not learn ticker-specific recommendations.
- Do not treat every AI-related company as a beneficiary.
- Do not use absolute price movement as proof of alpha when a relevant benchmark also moved.
- Do not ignore prior runup; continuation confirmation is different from early discovery.
- Do not promote broad AI beta into a scarce-layer thesis without identifying the constrained layer.
